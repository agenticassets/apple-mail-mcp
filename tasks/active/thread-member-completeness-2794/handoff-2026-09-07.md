# Thread member completeness (AGENTIC-2794) — handoff 2026-09-07

**Branch:** `fix/thread-member-completeness` from `origin/main` at `73a7532`.
**Scope:** one reported symptom, five root causes, four sub-issues.

## Reported symptom

Thread attachment retrieval silently omitted earlier conversation members. A
conversation with **9 members across 3 mailboxes** came back as 5, and every
completeness signal in the payload said the result was whole.

## Reproduced live before any fix

Against a reachable Exchange account, using repo source (never the installed
plugin — MCP tools execute the *installed* payload and return a clean answer
from stale code).

| Step | Result before | Diagnostic emitted |
|------|---------------|--------------------|
| `search_emails` subject + `date_from`, limit 20 | 4 of 9 | `scan_ceiling_reached: null`, `warnings: null` |
| `list_email_attachments` newest reply | signature image only | none |
| `list_email_attachments` Sent-resident member | `{"items": [], "returned": 0}` | none — indistinguishable from "id not found" |
| `get_email_thread` 3 mailboxes, `recent_days=14` | 5 of 9 | `matched=5 returned=5 render_incomplete=false candidate_scan_incomplete=false errors=null` |
| `export_emails(scope="thread", mailbox="All")` | `Error: Mailbox not found: All` | — |
| `export_emails(scope="thread", mailbox="Inbox")` | 5 messages, 3 signature images | reported as unqualified success |

Scan-bound proof, same anchor and mailboxes, only the bound varied:
**50 → 6.8 s / 5 members · 150 → 10.9 s / 9 members · 400 → 10.9 s / 9 members.**
Cost is flat past 150; the missing members were a bound, not a limit of Mail.

## Root causes

1. **RC-1 `get_email_thread`** bounded its per-mailbox candidate scan by
   `max_messages` — the *return* limit. Asking for at most 50 members also
   meant examining only the newest 50 messages per mailbox, and nothing in the
   payload reported that the scan had stopped looking.
2. **RC-2 `search_emails`** sized its scan from the page (`limit + offset + 1`)
   and ignored `date_from` entirely, then compared `scan_ceiling_applied`
   against the wrong value so the marker never armed.
3. **RC-3 `list_email_attachments`** was INBOX-only with no mailbox parameter,
   and emitted no row for a zero-attachment message — so "found, has none" and
   "never found" were the same answer.
4. **RC-4 `mailbox="All"`** reached a by-name mailbox lookup on the anchor
   fetch and raised `Mailbox not found: All` for a documented argument.
5. **RC-5 `export_emails(scope="thread")`** hardcoded its lookup mailboxes and
   printed an unqualified success banner over a partial export.

## What changed

New module split (all under the 600 LOC budget): `search/thread_payload.py`
(pure-Python payload assembly), `search/anchor.py` (bounded anchor-mailbox
probe), `search/scan_cap.py`, `analytics/attachments_helpers.py`,
`analytics/export_thread_scope.py`.

`SCAN_BOUNDS` gains `THREAD_SCAN_BASE_CAP` / `THREAD_SCAN_DAYS_SCALE` /
`THREAD_SCAN_WINDOW_CAP` / `THREAD_SCAN_HARD_CEILING` and
`THREAD_ANCHOR_MAILBOX_PROBE_CAP`. The thread ceiling is a **deliberate
exception** to the 50-message `SEARCH_HARD_CEILING`; the reasoning and the
measurement above are recorded in the `constants.py` comment.

### Two flags, deliberately separate

`thread_incomplete` means **a bound the caller did not choose** cut the thread
short: scan ceiling, render shortfall, candidate-scan failure, a recovered
anchor, or a script error. `window_truncated` means the caller's own
`recent_days` cutoff stopped the scan. Folding the date floor into
`thread_incomplete` was tried and reverted: it fires whenever a mailbox holds
anything older than the window, which is nearly always, and a flag that is true
on every call is one callers learn to ignore.

## Live acceptance after the fix

Same account, same conversation, repo source.

| Check | Result |
|-------|--------|
| `get_email_thread` two explicit mailboxes | **8 of 8** reachable members, `thread_incomplete: false` |
| `get_email_thread(mailbox="All")` | **10 members across 4 mailboxes** in 13.4 s (was a hard error) |
| `get_email_thread(scan_messages=3)` | 1 member **and** `thread_incomplete: true`, `scan_ceiling_hit` naming both mailboxes and the bound |
| Anchor missed by a narrowed scan | appended with `anchor_recovered: true` plus a warning |
| `list_email_attachments` on the attachment-bearing member | 4 attachments, `complete: true` |
| `list_email_attachments` on a zero-attachment member | `returned: 0`, `complete: true`, id in `resolved_message_ids` |
| `export_emails(scope="thread", mailbox="All")` | **10 exported** with the thread caveats as `PARTIAL:` lines |
| Narrowed thread export | 1 exported, `PARTIAL:` lines, no unqualified success |
| Text mode | carries the matching `PARTIAL:` ceiling lines |

## Two defects the live run found that mocked tests could not

- `mailbox="All"` **silently narrowed the scan** to the anchor's own mailbox,
  because the anchor probe's answer overwrote `resolved_mailbox`. It returned 5
  members and looked correct. Fixed: the probe now sets only the anchor fetch's
  mailbox, never the scan scope.
- The date floor initially fed `thread_incomplete`, which made it true on every
  realistic call. Split into `window_truncated` (see above).

Neither was visible to any mocked test. This is the standing reason live
verification is required here, not optional.

## Follow-ups not taken in this branch

- `include_sent=False` bounds the export candidates but not the thread scan
  itself; a Sent-resident member can still be enumerated and then dropped.
  Worth a separate issue.
- Text mode reports `FOUND 0` when the anchor was recovered, because the text
  banner is rendered inside AppleScript while anchor retention happens in
  Python. JSON mode is correct. Documented, not changed.
